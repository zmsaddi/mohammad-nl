# وثيقة تصميم — نظام العهدة والخزينة والأرباح + تطوير العمولات

> **الحالة:** دراسة/تصميم. **لا تنفيذ على الكود إلا بعد موافقة صريحة.** المشروع في الإنتاج (Production) والبيانات المالية حسّاسة.
> **التاريخ:** 2026-05-20 · **النطاق:** مرحلتان في وثيقة واحدة.

---

## 0) ملخص تنفيذي

نضيف طبقة **خزينة (Treasury)** فوق النظام الحالي: لكل شخص يتعامل بالكاش **صندوق عهدة** برصيد جارٍ، وصندوق **رئيسي** يديره admin. كل حركة مال تصبح **حركة في سجلّ موحّد** ترفع/تخفض صندوقاً. هذا يجيب عن «أين المال ومن يحمله»، دون المساس بطبقة **الأرباح** التي تبقى مستقلّة (الشراء = تبادل أصل، ليس مصروفاً؛ الربح يُحتسب نقدياً عند التحصيل).

**المرحلة 2 (مستقلّة):** تطوير بسيط لحساب العمولات ليكون **حسب نوع المنتج (category)**، لمنع توليد عمولة تفوق سعر المنتج (إكسسوارات/قطع غيار).

---

## 1) المبدأ المحاسبي: طبقتان مستقلّتان

| الطبقة | تجيب عن | المصدر |
|---|---|---|
| **الخزينة (Treasury)** | أين المال؟ من يحمله؟ | أرصدة الصناديق + سجلّ الحركات (جديد) |
| **الأرباح/الخسائر (P&L)** | هل ربحنا؟ كم؟ | إيراد − تكلفة مبيعات − مصاريف − عمولات (موجود) |

قواعد ثابتة (محسومة):
- **الشراء ليس مصروفاً** — تحويل كاش→مخزون. التكلفة تُحتسب وقت البيع (COGS).
- **العمولات = مصروف** يقلّل الربح. **توزيع الأرباح ≠ مصروف** (يقلّل حقوق الملكية والكاش فقط).
- **أساس الربح = نقدي** (وقت التحصيل)، **سداد كامل**: البيع الآجل لا يُحتسب ربحه حتى يُسدَّد بالكامل (سلوك الكود الحالي — صفر تعديل). الكاش الجزئي يدخل العهدة فوراً، الربح ينتظر آخر دفعة.

## 2) نموذج البيانات الجديد

### 2.1 `cash_boxes` — الصناديق
```
id              SERIAL PK
owner_username  TEXT UNIQUE NOT NULL  (FK users.username ON DELETE RESTRICT)
type            TEXT NOT NULL CHECK (type IN ('main','custody'))
balance         NUMERIC(19,2) NOT NULL DEFAULT 0   -- كاش-cache، يُحدّث ذرياً
active          BOOLEAN NOT NULL DEFAULT true
created_at      TIMESTAMPTZ DEFAULT NOW()
```
- صندوق واحد فقط `type='main'` (يملكه admin؛ هو نفسه عهدته الشخصية + خزينة المشروع). بقية المتعاملين بالكاش (manager/driver) `type='custody'`.
- **البائعون لا يملكون صندوقاً** (لا يلمسون كاشاً).
- `balance` نسخة مُسرَّعة؛ المصدر الحقيقي = `SUM(signed_amount)` من الحركات (للمطابقة الدورية).

### 2.2 `cash_movements` — سجلّ الحركات الموحّد
```
id              SERIAL PK
date            DATE NOT NULL DEFAULT CURRENT_DATE
box_id          INT NOT NULL  (FK cash_boxes)
counterparty_box_id INT NULL  (FK cash_boxes)   -- للتحويلات الداخلية فقط (info)
signed_amount   NUMERIC(19,2) NOT NULL           -- (+) داخل ، (−) خارج
method          TEXT NOT NULL CHECK (method IN ('كاش','بنك'))
kind            TEXT NOT NULL CHECK (kind IN (
                  'opening','capital_injection','collection','refund',
                  'supplier_payment','expense','commission_payout',
                  'profit_distribution','funding','handover'))
source_table    TEXT NOT NULL    -- 'payments' | 'supplier_payments' | 'expenses'
source_id       INT  NOT NULL    -- | 'settlements' | 'profit_distributions' | 'cash_handovers' | 'cash_boxes'(opening)
created_by      TEXT
notes           TEXT DEFAULT ''
created_at      TIMESTAMPTZ DEFAULT NOW()

UNIQUE (source_table, source_id, kind, box_id)   -- منع التكرار (idempotency)
```
- **رصيد الصندوق = `SUM(signed_amount) WHERE box_id = X`**.
- **التحويل الداخلي** (تمويل/تسليم) = **صفّان**: المُرسِل `−amount`، المُستقبِل `+amount`، كلاهما بنفس `source_id` (من `cash_handovers`)؛ لذلك `box_id` ضمن مفتاح التفرّد.
- **الحركة الخارجية** (تحصيل/مصروف/سداد/...) = صفّ واحد.

### 2.3 `cash_handovers` — طلبات التمويل/التسليم (آلة الحالة)
```
id            SERIAL PK
kind          TEXT CHECK (kind IN ('handover','funding'))
from_box_id   INT NOT NULL (FK cash_boxes)
to_box_id     INT NOT NULL (FK cash_boxes)
amount        NUMERIC(19,2) NOT NULL CHECK (amount > 0)
method        TEXT CHECK (method IN ('كاش','بنك')) DEFAULT 'كاش'
status        TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','confirmed','rejected'))
initiated_by  TEXT NOT NULL
confirmed_by  TEXT
created_at    TIMESTAMPTZ DEFAULT NOW()
resolved_at   TIMESTAMPTZ
notes         TEXT DEFAULT ''
```
- الأزواج المسموحة (هرمية): `driver↔admin`, `driver↔manager`, `manager↔admin`. (المدير الوسيط حالة اختيارية.)

## 3) أنواع الحركات وكيف تتغذّى الطبقتان

| النوع | الصندوق المتأثّر | الطريقة | أثر الربح (P&L) |
|---|---|---|---|
| `opening` | افتتاحي لكل صندوق عند تاريخ القطع | كاش (+ بنك لـadmin) | لا شيء (رأس مال افتتاحي) |
| `capital_injection` | admin/main (+) | كاش/بنك | لا شيء (حقوق ملكية) |
| `collection` | صندوق المُؤكِّد للتسليم (+) | كاش/بنك* | يُحقّق الربح عند اكتمال السداد |
| `refund` | صندوق من ألغى (−) | كاش/بنك | يعكس ربح البيع (انظر §7) |
| `supplier_payment` | صندوق منشئ الشراء (−) | كاش/بنك | لا شيء (يقلّل ذمّة المورّد) |
| `expense` | صندوق منشئ المصروف (−) | كاش/بنك | مصروف يقلّل الربح |
| `commission_payout` | main (−) | كاش | لا شيء (دُفعت العمولة المستحقّة سلفاً) |
| `profit_distribution` | main (−) | كاش/بنك | لا شيء (حقوق ملكية) |
| `funding` | main/أعلى (−) ← custody (+) | كاش | لا شيء (تحويل) |
| `handover` | custody (−) ← أعلى (+) | كاش | لا شيء (تحويل) |

\* **قاعدة البنك (محسومة):** أي تحصيل `method='بنك'` يذهب **دائماً إلى صندوق admin**، بغضّ النظر عمّن أكّد التسليم. ⇒ **صناديق السائق/المدير كاش صافٍ**؛ صندوق admin وحده يخلط كاش+بنك، ويُبقى وسم `method` لمعرفة «الكاش القابل للصرف» لديه (يسوّي البنك خارجياً).

## 4) آلة حالة التسليم/التمويل (مزدوج التأكيد)

```
[pending] ──(الطرف الآخر يؤكّد)──► [confirmed]  ← هنا فقط تتحرّك الأرصدة (صفّا حركة)
    │
    └────(الطرف الآخر يرفض)──────► [rejected]   ← لا شيء يتحرّك
```
- أي طرف يبادر (طلب أو عرض)؛ في `pending` **لا يتحرّك أي رصيد** (لا تُكتب حركة).
- عند `confirmed`: تُكتب حركتا `cash_movements` **مرّة واحدة** (مفتاح التفرّد + تحديث شرطي `WHERE status='pending'` يمنع التأكيد المزدوج).
- التأكيد المزدوج هو **بديل مطابقة العدّ**: اتفاق الطرفين على المبلغ = الإثبات.
- **«مال في الطريق»:** بما أننا لا نكتب حركة في `pending`، تبقى الأرصدة = الواقع المؤكَّد دائماً.
- **بند تشغيلي للقرار:** الطلبات `pending` العالقة تظهر في صفحة إدارة المال؛ (اختياري) صلاحية رفض/إلغاء الطلب من المُبادِر، و/أو انتهاء صلاحية تلقائي.

## 5) العهدة السالبة (محسوم: سماح بلا حدّ + رؤية)

- يُسمح بخروج كاش حتى لو أصبح الرصيد **سالباً** (لا منع). يُرفع **تنبيه** فقط.
- **معنى السالب:** الشركة **تدين** للحامل (دفع من جيبه)؛ يُسوّى عند وصول تمويل/تسليم.
- **لا حدود مفروضة** — الرقابة بالرؤية: صفحة إدارة المال تُظهر لـadmin **أرصدة كل الصناديق لحظياً** (بما فيها السالبة).

## 6) حساب الربح + التوزيع + سلامة الفترات

- **الربح المحقّق للفترة (نقدي، مستقلّ عن التوزيع)** = `netProfitCashBasis + totalProfitDistributed` (محسوب فعلاً [db.js:3631](../lib/db.js#L3631)). نعرضه رقماً رئيسياً مستقلاً، مع «المتبقّي للتوزيع» منفصلاً.
- **سقف التوزيع** يبقى نقدياً (لا توزّع إلا ما حُصِّل). إن أُزيل طرح التوزيعات من «الربح» في العرض، يُعاد اشتقاق السقف كـ`المحقّق − ما وُزّع` (تجنّب التوزيع المزدوج — [db.js:3774](../lib/db.js#L3774)).
- **سلامة الفترات (تصحيح الإلغاء):**
  - الحالي: استرجاع الكاش يُسجَّل **بتاريخ اليوم** ([db.js:617](../lib/db.js#L617)) ✅، لكن قلب البيع إلى «ملغي» يُسقطه من تقارير شهر مُقفل **بأثر رجعي** ❌.
  - **المطلوب:** إلغاء بيعٍ من فترة مُقفلة يُسجَّل **عكساً في الفترة الجارية**، والفترات المُقفلة **لا تتغيّر**. آلية: علم/تاريخ «قفل فترة» + قيود عكسية بتاريخ اليوم.

## 7) صفحة إدارة المال (UI)

- **admin:** يرى كل الصناديق وأرصدتها (بما فيها السالبة)؛ يموّل؛ يؤكّد التسليمات الواردة؛ يطلب تسليماً من أي شخص؛ رأس المال؛ تقرير حركة كل صندوق.
- **manager:** يرى عهدته + (إن كان وسيطاً) عهدات سائقيه؛ يموّل سائقاً؛ يؤكّد/يطلب تسليماً.
- **driver:** يرى عهدته فقط؛ يطلب تسليماً/تمويلاً؛ يؤكّد التمويل الوارد.
- يمكن دمجها مع صفحات التوزيع/العمولات الحالية أو إفرادها (قرار UI لاحق).

## 8) معادلة الثروة (تحقّق الصحّة)
```
Σ(أرصدة الصناديق، بإشارتها) + المخزون(بالتكلفة) + ذمم العملاء
  − ذمم الموردين − العمولات المستحقّة غير المدفوعة
= رأس المال المُودَع + الربح النقدي المحتجز − التوزيعات
```
كل حدّ موجود في الكود: المخزون `inventoryValue`؛ ذمم العملاء `totalDebt`+`pendingRevenue` ([db.js:2371](../lib/db.js#L2371))؛ ذمم الموردين `getSuppliers(withDebt).remainingDebt` ([db.js:1549](../lib/db.js#L1549))؛ الربح المحتجز `netProfitCashBasis + totalProfitDistributed`. الصناديق = الجديد الوحيد.

## 9) خطة الهجرة الآمنة + ضمان عدم تأثّر الواقع الحالي (شرح شامل)

> هذا القسم هو الأهم: كيف نضيف الطبقة الجديدة **دون أن يتغيّر أي شيء في النظام العامل حالياً**، وبقدرة على التراجع الفوري في أي لحظة.

### 9.0 المبدأ الحاكم — إضافة فقط
**لا تعديل، لا حذف، لا إعادة كتابة.** كل ما نضيفه:
- **جداول جديدة فقط** (`cash_boxes`, `cash_movements`, `cash_handovers`, وقد أُنشئ `category_bonus_rates`) عبر `CREATE TABLE IF NOT EXISTS`.
- **لا** `ALTER` يغيّر/يحذف عموداً قائماً، **لا** تغيير أنواع، **لا** `UPDATE`/`DELETE` على بيانات تاريخية.

⇒ بيانات الإنتاج الحالية تبقى **سليمة بحكم البناء** (structurally untouched). لا توجد عملية تكتب فوق ما هو موجود.

### 9.1 لماذا لا نُعيد بناء التاريخ
لا يمكن استنتاج «أي صندوق حمل أي كاش» من البيانات القديمة: `created_by` نصّي وقد يكون فارغاً/`'system'` ([db.js:1856](../lib/db.js#L1856))، و`totalPurchases` رقم **استحقاق** (يشمل آجلاً غير مدفوع) لا كاش فعلي ([db.js:2211](../lib/db.js#L2211)). لذلك **لا نلمس الماضي إطلاقاً**؛ نبدأ التتبّع من **تاريخ قطع** للأمام فقط.

### 9.2 الهجرة على مراحل خلف علَم تشغيل (`TREASURY_ENABLED`)

| المرحلة | ماذا يحدث | أثر الواقع الحالي |
|---|---|---|
| **P0 — نشر صامت** | إنشاء الجداول الجديدة **فارغة**؛ العلَم = OFF؛ لا قراءة/كتابة فيها | **صفر** — النظام يعمل حرفياً كما هو |
| **P1 — كتابة ظلّية (shadow)** | كل حركة مال تُصدر حركة صندوق أيضاً، لكن **العرض والتقارير ما زالت من المنطق القديم** | **صفر على الأرقام المعروضة** — نكتب فقط في الجداول الجديدة |
| **P2 — القطع + الأرصدة الافتتاحية** | تاريخ قطع + عدّ نقدي فعلي → حركة `opening` لكل صندوق | **صفر** — إدخال أرصدة بداية فقط |
| **P3 — تفعيل العرض** | صفحة إدارة المال + القراءة من الأرصدة؛ العلَم = ON | يظهر الجديد؛ القديم يبقى صحيحاً |

> في أي لحظة وأي مرحلة: **إطفاء العلَم = عودة فورية للنظام القديم 100%.**

### 9.3 تاريخ القطع والأرصدة الافتتاحية (تفصيل P2)
1. اختر لحظة قطع (مثلاً نهاية يوم عمل، حركة منخفضة).
2. **عدّ نقدي فعلي** لكل حامل كاش (admin / managers / drivers).
3. أدخِل لكل صندوق حركة واحدة `kind='opening'` بقيمة المعدود وبتاريخ القطع.
4. **بلا أرصدة افتتاحية** لـ: ذمم العملاء (`totalDebt`/`pendingRevenue`)، ذمم الموردين (`getSuppliers withDebt`)، العمولات المستحقّة، المخزون — لأنها **مشتقّة حيّاً** من الجداول الحالية؛ إدخالها يدوياً = **ازدواج حساب**.

### 9.4 الضمانات الملموسة أنّ الواقع لا يتأثّر
1. **لا تغيير على مخطّط أو بيانات الجداول الحالية** → استحالة إفساد بيانات الإنتاج بنيوياً.
2. **علَم تشغيل**: OFF ⇒ لا مسار جديد يُقرأ أصلاً؛ النظام القديم بالكامل.
3. **عزل الكتابة الظلّية**: تكتب في جداول جديدة فقط؛ **لا تلمس** `sales/purchases/payments/expenses/...` ولا أي رقم في لوحة التحكم.
4. **اختبار مطابقة قبل التفعيل**: على نفس الفترة يجب أن يقارب
   `Σ(أرصدة الصناديق − الأرصدة الافتتاحية)` ≈ `صافي النقد القديم (cashFlowNetCash)`.
   أي انحراف غير مفسَّر = **إيقاف والتحقيق قبل P3**.
5. **هجرة idempotent**: `CREATE IF NOT EXISTS` + `.catch(ignoreExpectedDdl)` ⇒ تكرار التشغيل/إعادة النشر آمن (نفس نمط [_migrations.js](../lib/db/_migrations.js)).
6. **تراجع فوري**: إطفاء العلَم؛ والجداول الجديدة قابلة للإسقاط (`DROP TABLE`) دون أي أثر على البيانات القديمة.

### 9.5 إجراءات التحقّق بعد كل مرحلة
- **P0:** التطبيق يعمل بلا أخطاء؛ الجداول موجودة وفارغة؛ **لقطة أرقام لوحة التحكم قبل/بعد متطابقة**.
- **P1:** لكل حركة مال جديدة يوجد صفّ صندوق مطابق (مطابقة 1:1 على عيّنة)؛ أرقام التقارير القديمة **ثابتة**.
- **P2:** مجموع الأرصدة الافتتاحية = المعدود الفعلي.
- **P3:** **معادلة الثروة (§8) تتوازن**؛ أرقام الأرباح القديمة لم تتغيّر.

### 9.6 المخاطر وكيف تُطفأ
| الخطر | الإطفاء |
|---|---|
| جدول مفقود وقت الكتابة | الهجرة تُنشئه في P0 **قبل** أي كتابة؛ والكتابة خلف العلَم |
| سباق على الرصيد | زيادة ذرّية `balance = balance + delta` داخل `withTx` + قفل الصفّ |
| ازدواج إصدار الحركة | `UNIQUE(source_table, source_id, kind, box_id)` |
| تعديل شهر مُقفل عبر الإلغاء | قيود عكسية بتاريخ اليوم + قفل الفترات (§6) |
| النشر يُطلق Vercel deploy | P0 **صامت** (العلَم OFF)؛ لا سلوك يتغيّر حتى P3 |

### 9.7 ما الذي يُلمَس في الكود القديم (وكيف يبقى آمناً)
- نضيف **«إصدار حركة»** داخل المُصدِّرات الحالية (collection / expense / supplier_payment / settlement / distribution / refund) **خلف العلَم**: إن كان OFF، يُتخطّى السطر الجديد وتعمل الدالة حرفياً كما اليوم.
- **لا تغيير** على منطق حساب الأرباح القديم؛ نضيف فقط **عرضاً/قراءة** جديدة (الربح المحقّق المستقلّ + صفحة إدارة المال).

## 10) قواعد التنفيذ (تزامن + سلامة)
- **الرصيد:** `UPDATE cash_boxes SET balance = balance + $delta` (زيادة ذرّية داخل نفس `withTx` مع إدراج الحركة) — **لا** قراءة-ثمّ-كتابة (لأن `withTx` بمستوى READ COMMITTED — [_shared.js](../lib/db/_shared.js)).
- **منع التكرار:** `UNIQUE(source_table, source_id, kind, box_id)` — لأن المُصدِّرات الحالية تُدرج بلا حارس (نمط BUG-4 / double-tap).
- **الاسترجاع:** `kind='refund'`، `signed_amount<0`، بـ`source_id` خاص به (صفّ الاسترجاع)، لا يصطدم بالتحصيل الأصلي.
- **القيود:** `CHECK(method)`, `CHECK(kind)`, `FK box_id/counterparty NOT VALID`، وأن `counterparty_box_id NOT NULL` للأنواع `funding/handover`.
- **توجيه البنك** يُفرض في طبقة التطبيق عند نقطة الكتابة ([db.js:1850](../lib/db.js#L1850)/[1856](../lib/db.js#L1856)) + مسار التحصيل اللاحق.

# المرحلة 2 — تطوير العمولات حسب نوع المنتج

> **تتطلّب موافقتك الصريحة قبل التنفيذ.**

## أ) الوضع الحالي (مؤكَّد من الكود)
[calculateBonusInTx — db.js:2865](../lib/db.js#L2865):
```
عمولة البائع = (seller_fixed × qty) + (max(0, actual − recommended) × qty × seller_pct/100)
عمولة السائق = driver_fixed × qty
```
المعدّلات: عالمية (`seller_bonus_fixed=10`, `seller_bonus_percentage=50`, `driver_bonus_fixed=5` — [_migrations.js:532](../lib/db/_migrations.js#L532)) + تجاوز **لكل مستخدم** (`user_bonus_rates`). **لا يوجد معدّل حسب المنتج/النوع.**

## ب) المشكلة
الثابت **مبلغ مقطوع لكل قطعة** بصرف النظر عن سعر المنتج:
- دراجة 1500€ → عمولة 15€ ≈ 1% (مناسب).
- قطعة غيار 3€ → عمولة 15€ = **500% من السعر** (عبثيّ).

## ج) الحل المقترح (نفس الشكل + تفصيل حسب النوع)
جدول جديد للمعدّلات حسب **الفئة (category)** الموجودة أصلاً في `products.category`:
```
category_bonus_rates(
  category TEXT PK,
  seller_fixed NUMERIC, seller_percentage NUMERIC, driver_fixed NUMERIC
)
```
- في `calculateBonusInTx`: نجلب فئة المنتج المباع (`sale.item → products.category`)، ونحلّ المعدّل بالأولوية المقترحة:
  **تجاوز المستخدم > معدّل الفئة > الافتراضي العالمي.**
- مثال: «اكسسوارات/قطع غيار» → `seller_fixed=0` (نسبة فقط أو لا شيء)؛ «دراجات» → `10/50/5` كما هي.

## د) أسئلة تحتاج تأكيدك قبل التنفيذ
1. **الحبيبية:** حسب **الفئة (category)** — أوافق؟ أم تريد لكل **منتج** على حدة (أدقّ، إعداد أكثر)؟
2. **الأولوية:** تجاوز المستخدم > الفئة > العالمي — مقبول؟ (تنبيه: تجاوز المستخدم رقم واحد يطغى على كل الفئات؛ قد يعيد المشكلة.)
3. **حدّ أمان اختياري:** هل نضيف سقفاً «العمولة لا تتجاوز X% من سعر/ربح القطعة» كشبكة أمان إضافية؟
4. **الفئات الحالية:** ما قائمة الفئات الفعلية لديك (دراجات/اكسسوارات/قطع غيار/...) لأبني عليها؟
